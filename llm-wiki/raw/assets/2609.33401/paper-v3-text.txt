Evaluating System One Models for Agent Security Decisions:
Reliability, Calibration, and Selective Automation
YIXUAN LIU∗
, TraceStone and Nanyang Technological University, Singapore
Agentic software connects language models to tools that modify files and interact with external services.
Developers use model-based security checks to screen external content and user requests before agents act.
System One models answer developer-defined questions with probabilities over predefined answers such
as safe or unsafe, but classification accuracy alone does not establish whether these probabilities support
reliable automation. We evaluate Jev, Laya, Decider, and Bespoke Nimble against specialized classifiers and
language-model judges across prompt-injection detection, interaction-risk judgment, and harmful-request
screening, examining decision accuracy, calibration, and selective automation. (1) High overall accuracy and
low average calibration error can conceal attacks classified as safe with high confidence within particular
groups. Developers should test candidate models on the intended security task and examine errors within
relevant attack groups. (2) Policies selected under strict miss limits allow few test inputs automatically, and
choosing allow and block thresholds separately increases automation mainly through additional blocks.
Developers should verify limits on missed unsafe inputs and blocked benign inputs on independent data, and
report the allowed and blocked fractions separately. (3) Comparing predictions on the same inputs shows
that a language-model judge can detect unsafe inputs missed by a System One model, but can also repeat the
System One model’s confident mistakes and falsely flag benign inputs. Developers should test which missed
unsafe inputs their review rule forwards, then measure the review model’s misses and benign false alarms on
those inputs.

1 Introduction
Agentic software combines language models with tools that inspect and change external state.
Agents retrieve documents and use services to complete user tasks, or navigate repositories, edit
code, and execute tests [9, 30]. Unlike a standalone text response, an agent’s interpretation of
an input can affect files, accounts, or subsequent tool calls. Developers therefore need to decide
which information the agent may trust and which operations it may perform. Runtime enforcement
systems such as AgentSpec make these constraints explicit in software [28].
Tool access also creates security challenges. Instructions embedded in external content can
redirect an agent, and the requested task itself may involve harmful conduct [2, 12]. For example, a
document retrieved for summarization may contain an instruction to send private information to
an external address. A security check needs to assess that instruction in relation to the user’s task
before the agent acts on it. Model-based judges can screen such content, user requests, or interaction
records. Missing an attack can expose the agent to unauthorized behavior, while rejecting harmless
content can interrupt legitimate work.
System One models [27] are designed to make fast, structured decisions. They take an input
and a developer-defined question, then assign probabilities to predefined answers such as safe or
unsafe instead of generating a free-form response. Jev, Laya, Decider, and Bespoke Nimble offer
implementations of this interface [4, 7, 19, 26]. Figure 1 shows this process for three security checks.
The application gives the decision component both the input and a task-specific question, such as
whether a retrieved page contains a prompt injection. The model returns an unsafe probability. A
security policy converts that probability into an action: allow the page to reach the agent, block it,

Decision automation means handling an input without further review, either by allowing or
blocking it. We assess its usefulness on labeled data by measuring the fractions of unsafe inputs
allowed and benign inputs blocked. We use error limits as acceptance criteria for these observed
rates. For example, a policy meets a 1% miss limit on 100 unsafe evaluation inputs if it allows at most
one of them. These limits express the application’s tolerance for missed threats and interrupted
legitimate work. The policy makes decisions from model probabilities, and labels are used to check
its errors during evaluation. Sending every input for review meets both limits but provides no
automation.
Using probability cutoffs also requires understanding calibration, the agreement between reported
probabilities and observed outcomes [13]. If inputs assigned an unsafe probability near 0.8 are
well calibrated, about 80% should be unsafe. Prior work reports attacks classified as safe with high
confidence and errors repeated by multiple judges [5, 23]. Developers therefore need to validate
labels, probabilities, and the actions chosen by the policy together [1, 6]. Strong classification
accuracy alone does not establish how much work a policy can automate while meeting both error
limits.
We investigate the following question: When can developers use System One model judgments
and probabilities to automate security checks in agentic software? We evaluate judgments
and policies offline on WAInjectBench, R-Judge, and AgentHarm using their original labels. We
compare System One models with language-model judges and task-specific classifiers, and Decider
and Nimble with their base models. Three research questions organize the evaluation.
RQ1: How accurately do models make security decisions? We compare missed unsafe inputs and
benign false alarms across tasks and attack groups. The observed differences show why developers
should select models for the intended security check and examine attack groups that overall
rankings can obscure.

RQ2: How well calibrated are the unsafe probabilities? We assess the unsafe probabilities returned
by each model and test recalibration fitted on development data. Average calibration can conceal
confident misses, so developers should also check the observed unsafe fraction among inputs a
policy would allow.
RQ3: How many inputs can a fixed policy process automatically within the error limits? We compare
fixed policies under limits on missed unsafe inputs and blocked benign inputs, and assess language￾model judges as potential reviewers. Separately selected cutoffs can increase automation through
additional blocks, yet some policies exceed their limits on test data. Developers should therefore
verify both policy error rates on independent inputs and assess which errors a second judge corrects
or introduces among the cases selected for review.
The study makes three contributions:
• An empirical study connecting decision errors, probability calibration, and automatic secu￾rity checks across System One models, specialized classifiers, and language-model judges.
• Evidence that aggregate performance and probability quality do not consistently establish
how many inputs a software policy can process within fixed error limits.
• Engineering implications for validating security checks, choosing allow and block thresholds,
and selecting review judges, supported by a public replication artifact.
2 Background and Related Work
2.1 System One Models
The name System One evokes fast, intuitive System 1 thinking [27]. Answers are typed because
developers specify their format and allowed values, such as a Boolean, a category, or an ordered
score. For a prompt-injection check, developers supply a tool response and ask whether it is unsafe.
The model assigns probabilities to safe and unsafe without writing an explanation.
Jev reports answer probabilities [26], Laya uses encoder decision heads [7], and Decider and
Nimble score candidate answers with language-model backbones [4, 19]. Changing the question
and allowed answers lets developers reuse the same typed interface across security checks [27].
2.2 Agent Security Evaluation
Indirect prompt injection places attacker instructions in retrieved data and can redirect a language￾model application’s behavior [12]. Existing benchmarks evaluate several security judgments relevant
to agents: R-Judge labels interaction risk [31], AgentHarm supplies harmful and benign requests [2],
and WAInjectBench evaluates web-agent injection detection [18].
Detector evaluations document high-confidence false negatives under changes in attack distri￾bution [5] and false positives on difficult benign inputs [24]. For typed decision models, Sun et al.
show that outputs can follow an answer option’s name rather than its attached definition, even
when they satisfy the required format [25].
AgentDojo evaluates security and utility in an executable agent environment [9]. CaMeL con￾strains information flow [8], AgentSpec enforces developer-defined runtime constraints [28], and
ProbGuard predicts execution safety from agent states [29].
2.3 Calibration and Selective Prediction
Calibration measures whether predicted probabilities match observed outcome frequencies. Temper￾ature scaling fits a probability transformation intended to improve that match [13], while changes
in the input distribution can undermine it [21]. Selective classification and SelectiveNet defer
uncertain predictions, trading the fraction accepted automatically against their error rate [10, 11].

For alignment-failure detection, Guo et al. show that calibration averaged across benchmarks

probabilities and fixed decision rules across security tasks, and compare models’ errors to assess
their potential to review one another’s decisions.

3.2 Benchmarks and Data Partitions
The study uses three public benchmarks with their original annotations. R-Judge supplies complete
interaction records with binary risk labels, while AgentHarm divides requests into harmful and
benign sets. WAInjectBench annotates attack-derived text segments as containing explicit instruc￾tions (EI), which directly tell an agent what to do, or lacking them (no-EI) [18]. Both groups retain
their released unsafe labels, including attack-derived segments without direct commands. Each
probability is evaluated against the unsafe event defined by its benchmark. Decision inputs exclude
labels, risk explanations, hidden attacker goals, class-revealing filenames, and future outcomes.

WAInjectBench, a fixed stratified split assigns the remaining inputs to selection, confirmation, and
test. Identical inputs are grouped before splitting and represented once, preventing duplicates from
crossing partitions. Selection inputs determine thresholds that act as probability cutoffs for allowing
or blocking inputs. Confirmation and test inputs assess those settings without retuning. We call

3.3 Input and Output Standardization
For each task, adapters present the same complete benchmark input and safe/unsafe label definitions
through each model’s interface. We extract the predicted label and any available unsafe probability
from each response. Classification uses valid labels, while probability analyses use a label and score
from the same response (Section 5). We count the complete formatted input with each model’s
tokenizer and do not truncate benchmark records. The English Laya checkpoint uses a 2,048-token
budget. Nimble and its base-model control use their scorer’s accepted budget of 262,143 tokens,
with 2,155 tokens as the longest formatted input in this study.
Figure 3 illustrates a rule that allows inputs below 10.5% unsafe probability, blocks those above
89.5%, and sends the rest for review. Laya correctly labels both inputs, but the injection’s 52.87%
probability requires review under this rule, whereas the benign notice’s 10.18% leads to an allowance.
A correct label therefore need not lead to an automatic decision. Section 6 explains how we select
and evaluate these rules.
3.4 Statistical Analysis
We estimate 95% confidence intervals (CI) from 2,000 cluster-bootstrap resamples that keep related
inputs together. Paired comparisons use the same resampled inputs for both models. Groups
contain identical R-Judge inputs, WAInjectBench inputs from the same released source family, or
AgentHarm variants of the same original task across labels and augmentations. We also check
sensitivity to grouping R-Judge inputs by source family.
For paired differences in false-negative and false-positive rates, cluster-level sign-randomization
tests reverse the direction of each cluster’s difference under the null hypothesis that model identities
are exchangeable. Holm correction accounts for multiple comparisons within each benchmark and
error metric. McNemar’s test serves as a secondary check under the assumption of independent
inputs.

4 RQ1: Security Decision Quality
RQ1 asks how accurately models identify unsafe inputs. We compare missed unsafe inputs and
falsely flagged benign inputs, then examine how these errors differ by task, attack group, and model
adaptation.
4.1 Metrics and Comparison Populations
We treat unsafe inputs as positive and report Macro-F1, precision, recall, the false-negative rate
FNR = FN/(TP + FN), and the false-positive rate FPR = FP/(TN+ FP) on valid decisions. Here
TP, TN, FP, and FN are true-positive, true-negative, false-positive, and false-negative counts. Area
under the receiver operating characteristic curve (AUROC) and average precision (AP) measure
score ranking, with AP summarizing the precision–recall curve. Table counts 𝑁 denote the inputs
in each comparison. Every applicable model returns a valid label on every test input, enabling
same-input comparisons within each task.
4.2 Classification Results and Error Patterns
No primary configuration has the highest Macro-F1 on all three tasks, and similar scores can
accompany different miss and false-alarm rates. Tables 3 through 5 rank configurations by Macro￾F1 point estimates on 1,612 WAInjectBench, 236 R-Judge, and 352 AgentHarm inputs.
Nimble leads the primary WAInjectBench ranking, yet misses 8.1% of attack-derived inputs that
directly instruct the agent and 92.3% of those without direct instructions. Jev misses all 130 unsafe
no-EI inputs while falsely flagging just one benign input. Before selecting a model for a security
check, developers should examine its overall performance and miss rates within relevant attack
groups.

5 RQ2: Probability Calibration
Among inputs assigned an unsafe probability near 0.8, about 80% should be unsafe if the predictions
are calibrated. RQ2 examines this agreement across tasks and attack groups, then tests whether
recalibration fitted on development data improves test probabilities.
5.1 Probability Scores and Calibration Measures
For System One models, we use the unsafe probabilities returned by their decision interfaces.
For general judges, the score is the unsafe answer token’s probability divided by the combined
probabilities of the safe and unsafe tokens at the final answer position. GPT-4.1 and Qwen3-8B
use separate response configurations for classification and probability analyses, so their predicted
labels can differ between these analyses. Recalibration and policy evaluation use the same scoring
rule across all partitions. When required labels or scores are missing, we retain the first usable
retry regardless of whether its prediction is correct.

benchmark labels on confirmation and test inputs after thresholds are fixed. We also compare
model errors to assess potential reviewers.

6.1 Decision Policy and Error Measures
The policy compares unsafe probability 𝑝𝑖 with an allow threshold 𝜏𝐿 and a block threshold 𝜏𝐻 :

Inputs exactly at either threshold, or without usable scores, also escalate for review. Automatic
coverage is the fraction allowed or blocked, while allow coverage counts only allowances. Both
use all partition inputs as the denominator. We report them separately because high coverage can
result from blocking many inputs while allowing few to proceed. The unsafe-miss rate Missauto is
the fraction of unsafe inputs allowed, and the benign-blocking rate FBauto is the fraction of benign
inputs blocked. A low miss rate can therefore come from allowing almost nothing. Allowed-set
risk instead measures the unsafe fraction among allowed inputs, with zero-denominator ratios
undefined.
6.2 Policy Selection and Independent Confirmation
Symmetric policies link the thresholds through 𝜏𝐿 = 1−𝜏𝐻 . We evaluate 101 pairs with 𝜏𝐻 increasing
from 0.5 to 1 in steps of 0.005. For each allowed miss rate 𝜖 ∈ {0.01, 0.05, 0.10}, we choose the pair
with the highest automatic coverage on selection inputs, subject to Missauto ≤ 𝜖 and FBauto ≤ 0.05.
If coverage is tied, we prefer more automatic allowances, then the larger 𝜏𝐻 . The search includes
(𝜏𝐿, 𝜏𝐻 ) = (0, 1), which sends every input for review and automates no decisions.
Selected thresholds remain fixed for confirmation and test, including policies that fail confirma￾tion. A policy passes only when both error rates meet their limits. These checks use WAInjectBench
and R-Judge, which provide the required partitions (Table 2).
Small samples and strict error limits. A 1% miss limit requires zero misses among R-Judge’s 74
unsafe selection inputs and 49 unsafe confirmation inputs, because a single miss exceeds the limit
in either set. WAInjectBench has 167 and 111, respectively, permitting one miss in each. With so
few permitted errors, individual inputs can determine whether a policy passes, and larger samples
are needed to estimate rare-error rates precisely. The benign-blocking limit is similarly sensitive to
individual errors. R-Judge confirmation permits at most two blocks among 44 benign inputs under
its 5% limit, while test permits five among 111. Cluster-bootstrap intervals describe uncertainty
from the sampled interaction records and attack sources.

6.5 Confidence Ranking and Identical Scores
Figure 10 ranks inputs by maximum class probability and counts predictions as automatic decisions
from highest to lowest confidence. A safe prediction allows the input and an unsafe prediction
blocks it. Inputs with equal confidence enter together. The plotted error rate is the fraction of these
decisions that are wrong.
Thresholds cannot separate correct and incorrect decisions with the same score. Jev
assigns 𝑝𝑖 = 0 to 1,320 shared WAInjectBench inputs, including 102 misses, and 𝑝𝑖 = 1 to three
correct predictions. Automatically allowing the zero-score inputs and blocking the one-score inputs
covers 82.07% at 7.71% error. Any positive allow threshold admits all zero-score inputs, including the
missed attacks. An independent block threshold can reject high-score inputs but cannot distinguish
attacks from benign inputs within that zero-score group. On AgentHarm, Jev’s predictions with
maximum class probability one cover 126 of 352 inputs with two errors (1.59%), showing that the
same confidence accompanies different observed error rates across tasks.
6.6 Language-Model Judges as Potential Reviewers
An application can send uncertain inputs to a language-model judge for review. To assess models
for this second-judge role, we compare their predictions with those of each System One model on
the same inputs [23]. We count an error as corrected when the judge predicts the benchmark label
for an input the System One model misclassifies. A judge can correct the first model’s missed attack
only when the review rule forwards that input, so selecting the reviewer also requires checking
which cases the rule leaves unreviewed.
We compare four System One models with seven general judges on 1,612 shared WAInjectBench
inputs, 236 R-Judge records, and 352 AgentHarm requests. Including task-compatible specialists
gives 100 model pairs evaluated on the same complete test inputs within each task. For each class,
a judge can correct or repeat the System One model’s errors, or make errors on inputs that model
classified correctly. Figure 11 reports the fraction of the System One model’s errors corrected by

attacks missed by Jev but misses 33 that Jev correctly flags. Its own miss count is therefore 190,

7 Discussion
7.1 Component Integration and Error Handling
Applications need explicit handling of input limits, invalid answers, missing scores, and network
failures, sending inputs without usable scores for review. Deployment measurements also depend
on the configuration: service routing, queueing, caching, and reasoning settings affect latency and
API charges, while local backends and precision can affect scores.
7.2 Implications for Developing Agentic Software
Define the security task before selecting a model. Developers should specify the behavior to
prevent, the legitimate work to preserve, and where the check affects the workflow. Checks on
retrieved content, interactions, and user requests need different inputs and labels. For example, a
request to summarize a dangerous command differs from a request to execute it, so the question,
answer definitions, and available context should make the intended judgment explicit.
Choose models for the application’s requirements. Developers should compare candidates
on representative labeled inputs at tolerable miss and false-alarm rates. The comparison should
include task-compatible specialists alongside reusable typed components and general judges, taking
context capacity and deployment resources into account. Because rankings and adaptation gains
=== PAGE 24 ===
Yixuan Liu
vary by task, candidates need to be evaluated with the question and input context the application
will actually use.
Validate labels, probabilities, and policy actions separately. Developers should check
classification errors across relevant input and attack groups, then assess whether probabilities
reflect observed outcomes, particularly among inputs that would be allowed. Recalibration should
be fitted on development inputs and cutoffs selected on selection inputs, with both frozen before
independent checks. Policy validation should count unsafe inputs allowed, benign inputs blocked,
and inputs sent for review, reporting allowed and blocked fractions separately because additional
blocks do not enable more work to proceed. This staged validation supports component testing
and monitoring in production ML engineering [1, 6].
Choose which inputs to review and which model reviews them. The second judge receives
the inputs selected for review, which can differ substantially from the full workload. Developers
should use labeled inputs to measure which missed unsafe inputs the rule forwards and which errors
the judge corrects or introduces. If validation reveals confident mistakes that an uncertainty-based
rule leaves unreviewed, developers should reconsider the question, context, model, or review rule,
then test the revised combination.
Maintain validation as the software changes. Developers should record the model version,
question, input construction, and cutoffs as one tested configuration and revalidate it whenever
any part changes. Monitoring should include automatically handled inputs as well as reviewed
ones, because errors in the former may never reach the second judge. Applications should define
an explicit fallback for configurations that fail these checks.
Enforce permissions independently of model judgments. Access controls should restrict the
resources an agent can use, while deterministic runtime checks enforce permitted operations [8, 28].
A safe prediction should not override these permissions, and the combined system should be
evaluated by measuring successful attacks and completion of legitimate tasks.
8 Threats to Validity
Internal validity. Comparisons depend on prompts, answer-label order, context limits, reasoning
settings, and services. Response sampling and output formats can affect scores. Recalibration
uses only development data, and threshold selection uses only selection data, with no retuning on
confirmation or test. Rare errors and few source clusters limit interval precision. Construct validity.
AgentHarm labels harmful requests as unsafe, while WAInjectBench labels attack-derived text
as unsafe even without explicit instructions. The EI/no-EI, threshold-sensitivity, and cross-model
error analyses are exploratory. Our finite grid restricts allowance thresholds to at most 0.5 and
blocking thresholds to at least 0.5. Other policies may yield different trade-offs. External validity.
Public benchmarks may overlap training data, and unsafe-input proportions affect precision, AP,
and calibration. Results may differ for adaptive attacks, other languages, and multimodal inputs.
Hosted model revisions and service behavior can change between runs. Protection also depends on
the agent, environment, guard placement, and handling of blocked requests, requiring validation in
the target system.
9 Conclusion
Our evaluation shows that aggregate rankings and calibration metrics can conceal attacks confi￾dently classified as safe, and that strong performance on one security task does not consistently
transfer to another. Policies selected under strict error limits allow few test inputs automatically,
while choosing the allow and block thresholds separately increases automation mainly by rejecting
more inputs. Developers should therefore select models for each security task, verify policy error
